# 栖序 QIXU：产品设计

**本轮只完成方案整理，未授权进入新版工程。** 本文整合初版设计、用户复核意见和公开表达研究，是当前产品需求的权威入口；技术报告末尾的启动 prompt 仅用于交接，读取本身不构成开工授权。实现选择、实验步骤和 A–E 清单见 [技术报告](technical-selection-report.md)，实际启动见 [README](../README.md)。

栖序是虚构高端香水品牌的顾问写作助手：围绕客户当前问题生成三条完整微信候选，由顾问选稿、修改和决定使用。客户、商品、政策和活动均为合成资料。PDF 等附件用于理解交付要求，其中的联系地址或其他指令不构成发信、发布或外部操作授权。

## 一、拆解任务：范围与工作流

| 状态 | 范围 |
|---|---|
| 本地 v1 已实现 | Python／Streamlit／Pydantic／单一模型 API 共用核心；输入资料、六场景三稿、选稿编辑、批量运行、记录及八列导出。已有 50 例、150 条真实候选；首轮 49/50 成功，单例技术重试补齐。 |
| 下一版规划，未实现 | 先独立 Web App；持久客户与会话、相关商品展示、写作设置、多语言、三稿原位编辑复制、可纠正偏好和自动草稿。之后再验证企业微信／微信客服接入。 |
| 当前质量与材料限制 | 文案和事实仍有已知缺陷；真人评分为 0，历史 AI 操作截图仍有缺件。应用能运行不等于 A–E 完整，也不等于内容已经可发送。 |

用户要求**先方案与相应模块设计，再进入工程；产品形态先 Web，后企业微信／微信客服**。本轮确定功能、数据与接口；每阶段编码前先明确行为，工作台在前端编码前完成桌面／手机流程设计。先解决内容质量和连续工作，再验证渠道入口。界面只围绕顾问工作，不设计订阅、套餐升级或营销首页；版本改进记录仍属于 PDF 的 E 材料。

### 六场景与最小资料

| 场景 | 要完成的工作 | 必要输入与关键边界 |
|---|---|---|
| 生日与节庆 | 得体表达关心 | 明确的祝福缘由、称呼和关系背景；不猜年龄、家庭，不强行带货。 |
| 产品推荐 | 为自用或送礼缩小选香范围 | 使用者、已知喜好与排除项、预算、商品；未知关键信息可追问，不套用购买者偏好。 |
| 购后关怀 | 回应体验或已有问题 | 已购商品、当前反馈，涉及售后时才取相关政策；不忽略问题继续营销。 |
| 沉睡唤醒 | 自然重新开启交流 | 过去互动、已知兴趣、联系意愿；拒绝联系时不生成主动召回消息。 |
| 活动邀请 | 说明活动与客户的相关性 | 日期、时区、地点、内容、参与条件；意向、登记与门店确认分开。 |
| 价格异议 | 回应觉得贵、渠道比较或折扣请求 | 客户原话、同款规格与价格、相关政策；不擅自优惠或贬低其他渠道。 |

工作流：**打开客户与会话 → 理解这轮需求 → 核对相关商品 → 生成三条 → 原位编辑、复制 → 保存后下次继续**。资料足够的新客户不必先建完整档案；历史聊天可以为空。每条候选都应独立完成回复，不能三条拼起来才有答案。

### 工作台只显示当前需要的信息

桌面保留客户／会话列表、当前消息、相关商品和三条候选；本次需求与商品卡可就近展开。场景、输出语言和生成操作容易找到，语气、目标、篇幅放相邻写作设置。手机将列表和资料收进可关闭抽屉，避免侧栏遮挡正文。

三条候选各自在原位置编辑，提供复制当前正文、恢复机器原稿和保存状态。复制读取点击当下的文字，未保存修改也应能复制；成功后才提示已复制。新消息或重新生成不覆盖正在编辑的稿件，新生成保留为另一组。选稿、编辑、复制和实际发送是不同动作。

API 状态、资料维护和导入导出放设置；开发案例、运行详情、批量与评价放管理工作区。主页面不呈现原始 JSON 或技术运行 ID。颜色、字体、留白在后续桌面／手机设计中确定，美化以阅读和操作为目的。

### 资料与记忆的归属

| 对象 | 当前基础与下一版职责 |
|---|---|
| 品牌、商品与政策 | 当前一份品牌规则、一份政策、四款香水六个 SKU、两个活动；保留规范名、规格、币种、来源和版本。历史商品身份也要展开，筛选子集不能冒充完整目录。 |
| 客户与收礼人 | 当前八个合成客户；长期信息分别归属于对应人物，购买者与使用者不能混为一人。 |
| 临时会话 | 本次预算、对象、排除条件、语言语气和未解决事项；会话结束不自动升级为长期偏好。 |
| 原始消息 | 原文、作者、时间、来源与会话；粘贴导入和真实渠道接收分开。摘要关联原消息，保留未确认事项。 |
| 偏好证据 | 属于谁、明确表述或推测、原消息引用、时间、确认／撤销状态；允许顾问纠正。 |
| 生成与草稿 | 输入版本、三条机器原稿、人工修改及选用／复制动作分别保留；草稿不得冒充已发送历史。 |
| 测试与写作参考 | 当前 50 源例及独立评价预期；`approved.jsonl` 尚为空且未被生成器加载。后续只加入经审核的少量虚构示例。 |

刷新、重开会话和重启服务后恢复已保存内容，切换客户不串档；原始运行证据继续保留。当前明确需求优先于旧偏好，冲突保留来源并提醒核对，不由模型悄悄重写档案。库存、留香、甜感等未提供时保持未知；香调描述不是配方、含量或功效。[数据路径与保存合同](technical-selection-report.md#data-paths)

## 二、解释原理：事实先于文风

推荐与价格场景要有具体商品、规格、价格和匹配理由；祝福或简短致谢不为了“有产品”硬塞销售。内部限制用于约束生成，仅在影响当前决定时向顾客解释。客户说实际闻起来偏甜时，不用目录标签否定体验。

| 写作设置 | 首阶段选项 | 保持不变的约束 |
|---|---|---|
| 本次目标 | 回答问题、帮助选择、提出下一步；场景给默认值 | 不把投诉、拒绝或简单致谢变成推销。 |
| 语气 | 日常自然、温和关怀、简洁直接 | 称呼与关系有依据，不因语气变化增加事实或承诺。 |
| 篇幅 | 简短、标准 | 按语言设软目标，不截掉必要条件或关键信息。 |
| 输出语言 | `zh-CN` 默认、`en` 可选 | 固定三条；语言不改变地区政策、CNY、规格、日期或时区。 |

输入接受中文、英文及中英混合；输出由顾问明确选择，识别输入语言不能覆盖设置。英文商品名未经审核时保留规范中文名。正式 PDF 的 C 表仍为五十例、每例三条中文；英文结果独立导出。

三条应在侧重点或合理下一步上有选择价值，而不只是换词。必要事实可以相同，不为差异虚构三种商品或承诺。策略标签、事实依据和风险提示只给顾问看，复制仅包含对客正文。

### 写作规则与公开参考

拟采用有版本的 `qixu-wechat-writing` 规则包：确认对象与当前问题 → 提供相关事实 → 直接回应 → 组织三种完整表达 → 删去无关规则和冗余。**规则与审核示例必须在应用运行时显式加载**；仅安装开发用 skill 不会改变模型回复。本轮不创建或安装 skill，不把拟写样例冒充实验结果。

2026-11-06 核验的三项一手参考如下，页面未标明正文发布日期。这些是公开 FAQ／服务介绍，未取得可验证的私人顾问对话；下面是产品设计借鉴，不是效果证明。

- [Hermès 中国礼物 FAQ](https://www.hermes.cn/cn/zh/faq/online-shopping/gifting/)：先回答具体问题，再给相关选项；明确购买者与收礼人。
- [Jo Malone 客服 FAQ](https://www.jomalone.com/customer-service/faq)：限制说明之后给可执行帮助，只索取当前必要资料。
- [Diptyque 顾问服务介绍](https://diptyqueparis.com/en-eu/pages/maison-diptyque-paris)：以交谈帮助选香，资料不足时问能缩小范围的问题。

仅借鉴表达结构，不导入真实品牌的价格、礼盒、试用装、活动和退换承诺；不把宣传页的形容词当成私聊标准。自然度以顾问愿不愿发送及需要怎样改稿判断，不使用“AI 检测分数”代替评价。

### 偏好、推荐与自动草稿

商品偏好和沟通偏好分别保存。“妹妹不喜欢甜香”属于妹妹；顾问常选短稿不能证明顾客喜欢短回复；未回复、未购买不能直接推断为讨厌产品。模型可提取待确认偏好，顾问可确认、停用或撤销。

推荐先按当前对象、预算硬上限和明确排除项筛选，再按已确认的香调／甜感匹配排序，初期匹配维度等权并展示理由。未知属性不算满足条件，无合适商品不暗中放宽预算。少量合成客户不足以宣称已经训练出推荐算法。

先手动粘贴／导入聊天验证续聊，后续再核验一种企业微信／微信客服渠道；读取客户资料不等于可以读取任意微信聊天。新消息到达后可自动生成三条草稿，允许按会话关闭；上下文变化时标明旧稿过时，不覆盖人工编辑。自动生成不启用自动发送，明确拒绝联系优先于召回设置。[扩展边界](technical-selection-report.md#extension-contracts)

## 三、展示实验：现状与待验证改动

已审阅 v1 真实输出，发现历史商品名误写“青榄／青澜”、选中 50 mL 被误认为唯一规格、祝福和致谢暴露无关内部限制、三稿差异偏弱。历史资料中没有完整的顾客→顾问→顾客连续追问；现有落盘记录也不能直接恢复工作会话。23 项程序测试曾通过，只支持所测软件路径，不能证明文案质量。[已有 AI 审阅证据](../artifacts/submissions/initial-local/evidence/ai-formal-review.md)

本轮没有新模型实验或人工评分，不能声称上述缺陷已经修复。下一轮先修商品身份和事实范围，再固定事实比较写作规则，随后验证设置、多轮、页面与恢复。具体实验及证据保存在[技术验收计划](technical-selection-report.md#acceptance)，产品侧核心覆盖为：24 例语言补充组（六场景 × 英→中、中→英、英→英、混合→中），六条多轮序列，以及编辑复制、恢复会话和客户隔离。新增测试尚未执行。

## 四、判断结果：可用的定义

| 评价 | 判定 |
|---|---|
| 直接用 | 对象、事实、回应和语气都合适，无需改动。 |
| 小改可用 | 核心内容正确，只调整称呼、语序、标点、措辞或删去冗余。 |
| 实质改写 | 要改人物、商品、金额、政策、推荐方向，或补上遗漏的重要顾虑。 |
| 弃用 | 无法在原稿基础上合理完成任务。 |

把错误价格改一个数字仍是实质改写。只说“随时联系我”却没有回应价格顾虑，也不能判可用。一条好稿不能抵消另两条的严重错误；三条共享输入，不能当三个独立客户任务。

项目质量目标是三条独立完整、关键人物／商品／价格／承诺无误，且真实配对评价显示可发送覆盖和编辑负担改善、事实不退步。旧集回归仍对照技术报告中既定的 24/30、分场景与三稿差异门槛；新增语言／未见组须在运行前冻结适用标准，不能仅凭比初版略好宣称达标。这些均是项目标准，**不是 PDF 指定分数或规定全数人评、双人复核**。评价人数、覆盖量及限制如实报告，英文自然度须由具备相应语言能力的人评阅。

离线替身测试、真实模型运行、真人评价分开报告；AI 审阅不填人工分数。新旧稿隐藏版本并随机排列，保留具体修改和理由；没有计时不声称省时。保存首轮失败和关联重试，不重抽好稿掩盖内容问题。应用状态与 A–E 各自完成度见[交付清单](technical-selection-report.md#submission-package)。
