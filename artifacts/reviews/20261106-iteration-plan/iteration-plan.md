# 栖序 QIXU：初版自查与下一轮方案

日期：2026-11-06。状态：**供下一轮设计使用的方案，尚未实施**。

用户已确认：多语言输入／输出；先独立 Web App，再企业微信／微信客服。本轮范围是自查、公开资料研究、保存初版和形成方案。未修改应用、提示、合成业务资料或既有交付；未新增模型调用、人工评分或界面效果截图。两份主报告仍保留在 `docs/`，本文件不是第三份主报告。

## 一、拆解任务：先提高顾问工作的完成质量

下一版要完成一条连续的工作流：**打开客户与会话 → 理解这轮需求 → 确认相关商品 → 得到三条可发送的候选 → 原位修改、复制 → 下次接着处理**。自动接收聊天是这条工作流的后续入口。

第一优先是事实与文案，其次是持久会话和页面，最后验证渠道接入。用户提到的“升级部分”按减少无关功能处理：不设计订阅、套餐升级、营销首页或与顾问工作无关的模块。版本改进及缺陷记录仍需保留，因为它们属于 PDF 的 E 材料。

### 七条建议与 PDF 的关系

| 建议 | 对 PDF 的帮助 | 方案决定与顺序 |
| --- | --- | --- |
| 1. 从本地走向长期使用 | 在线演示方便检查；云部署本身并非 A–E 必交项 | 先稳定共用核心，再做可部署的独立 Web 工作台；保留原 Streamlit 作为基线 |
| 2. 只保留工作相关内容 | 更易展示顾问实际操作；减少提交时无关内容 | 主流程只围绕客户、会话、商品和文案；研发及评价仍有独立入口 |
| 3. 有商品、有自然语气、语言设置和写作 skill | 直接影响题目的私人交流感、品牌感及 B/C/D/E | 第一优先；先中文质量，再增加中英输入输出验证 |
| 4. 客户数据库与临时上下文 | 支撑完整输入、多轮连贯和可复现检查 | 与会话合同一起设计；分开长期事实、本次需求和原始消息 |
| 5. App／插件，设置收起 | 改善工具使用与可选演示 | 先响应式 Web App；设置独立；渠道权限核验后再接入 |
| 6. 美化、原位编辑和一键复制 | 直接支持顾问选稿、改稿及操作证据 | 页面围绕这三个动作设计；先确认流程，再确定视觉细节 |
| 7. 偏好、推荐、聊天捕捉与自动生成 | 可增强个性化与输入完整性；全自动接入并非必交项 | 先可解释偏好规则、人工导入消息；随后一种真实渠道自动生成草稿 |

PDF 要求六场景、三条完整中文微信候选及 A–E；数据库、多语言、云部署并不是额外硬性要求。项目采用的真人可发送性评价与复核方法用于提供可信证据，不能写成 PDF 指定了某个评价人数或固定人评工作量。

## 二、解释原理：功能与数据方案

### 1. 让产品事实和顾客这句话先于文风

保持现有 Python / Pydantic / 单一模型 API 生成核心，先修事实装配。输入快照分清：购买者、使用者／收礼人、本次需求、长期档案、本轮消息、相关商品和本题相关政策。客户明确的新要求优先于旧档案；冲突保留来源并提示顾问核对，模型不能悄悄修改长期档案。

历史商品 ID 要映射到规范名称；本次推荐加载实际可选 SKU 和筛选范围。推荐、价格场景提供具体名称、规格、价格和匹配理由；生日、简短致谢不为了“有产品”硬塞销售内容。未知库存、留香或偏好不补造，用户未问到且不影响选择时也不逐条宣读未知项。

前三个写作设置采用少量清楚的选项：

| 设置 | 初期选项 | 行为约束 |
| --- | --- | --- |
| 本次目标 | 回答问题、帮助选择、提出下一步；随场景给默认值 | 不把投诉或拒绝转换成促销目标 |
| 语气 | 日常自然、温和关怀、简洁直接 | 事实、关系称呼和服务权限不随语气变化 |
| 篇幅 | 简短、标准 | 按语言定义软目标；不能截掉价格、活动时间或必要条件 |
| 输出语言 | 简体中文默认、English | 候选固定三条；语言不改变业务地区、货币和政策 |

三个候选分别提供有用的表达选择，所有候选都独立完整。事实相同可以保留，合理下一步不同时才变化；不强行制造三种产品、三种承诺或夸张人设。策略标签、依据、风险提示留在工作台，复制时只含消息正文。

语言输入支持中文、英文、中英混合；输出第一阶段明确支持中英两种，其他语言之后根据实际需求扩展。英文商品名尚未审核时保留规范中文名。不能以“至少一个汉字”的现有检查判断整段中文质量，也不能放宽后让英文混入正式 C 表。

### 2. 写作 skill 的实际落点

拟定项目写作规则包 `qixu-wechat-writing`。后续可将同一规则包包装为开发审稿 skill，但生成器必须显式加载规则和示例，保存版本与摘要。给开发助手装技能本身不会自动改变应用发给模型的提示。

规则按“先答当前问题 → 只用相关事实 → 给一个合理下一步 → 删除无关内部解释”组织；规则检查与少量人工审阅样例配合，不采用所谓 AI 检测分数。避免绝对禁词表：顾客问到库存时如实说未知是必要的，生日问候里主动解释库存未知则无关。

例句只从开发场景另写虚构 QIXU 回复，记录来源、适用目标、使用理由和审阅状态。未审阅示例不得放入 `approved.jsonl`；评分预期与保留案例输出仍不进入提示。规则包由 CLI、Web 和未来渠道共用，避免三条生成路径逐渐分叉。

本次已查 [Hermès 礼赠 FAQ](https://www.hermes.cn/cn/zh/faq/online-shopping/gifting/)、[Jo Malone 客服 FAQ](https://www.jomalone.com/customer-service/faq)、[Diptyque 顾问服务介绍](https://diptyqueparis.com/en-eu/pages/maison-diptyque-paris)。可借鉴直接回答、只索取必要资料、区分意向与确认的服务结构；这些是公开 FAQ／服务介绍，没有可验证的私人聊天实录。外部价格、试用装和退换承诺不转入 QIXU。[完整研究与拟写样例](luxury-reference-research.md)。

例如，“给妹妹选的话，可以先看青岚。它是柑橘与雪松的气息，甜感低，50 mL 是 980 元，在您的预算内。”可展示“对象—商品—理由—价格”的方向。**这是本次方案拟写，不是新模型实验、真人回复或改进成绩。** 后续需用真实同输入实验判断是否更自然。

### 3. 工作台的功能分区（不是最终视觉稿）

主页面桌面左侧为客户／会话列表，中间为当前消息和三条候选；相关商品卡和本次需求可以就近展开。顶部保留场景、输出语言和生成操作，语气／篇幅收在紧邻的写作设置中。手机把列表和资料放入可关闭抽屉，优先保留正文阅读空间。

每张候选卡原位修改，分别显示“已保存／保存中／保存失败”，提供复制当前正文、恢复机器原稿。选稿与重新生成分开；重生成建立新组并保留旧稿，新消息到来不覆盖正在编辑的文字。记录编辑与复制，但复制不等于实际发送。

设置入口容纳服务端 API 配置状态、客户资料维护、商品目录、数据导入导出。开发案例、运行详情和评价放独立管理工作区，主页面不显示原始 JSON 或技术运行 ID。模型密钥只在服务端读取，不发到浏览器。

视觉设计下一阶段再出桌面／手机低保真稿，先确认层级和操作，再选颜色、字体与留白。遵循 [用户偏好记录](../../../DESIGN.md)，不在本轮擅自定品牌视觉。

一键复制从点击当下的编辑框取值，成功后才提示已复制；失败保留正文供手动复制。部署采用 HTTPS，实际验证目标浏览器，因为 Clipboard API 的安全上下文和用户激活要求会影响行为。[MDN Clipboard](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API#security_considerations)

### 4. 客户数据库与临时上下文

下一版建议单实例服务与持久磁盘 SQLite，模型调用放在写事务外。当前规模不需要向量库或推荐模型训练。出现多个应用实例并行写、持续写入冲突或集中运维需要时，再单独评估 PostgreSQL；不同时实现两种数据库。[SQLite 官方适用说明](https://www.sqlite.org/whentouse.html)

| 数据对象 | 必需信息与职责 |
| --- | --- |
| 客户／人物 | 稳定 ID、称呼、关系、确认的长期信息；收礼人与购买者分别归属 |
| 会话 | 客户 ID、本次目标、临时预算／对象／排除条件、语言语气、未解决事项、状态 |
| 消息 | 原文、作者、时间、来源、会话 ID；未来附渠道消息 ID；导入与真实渠道消息区分 |
| 偏好证据 | 属于谁、值、明确表述或推测、原消息引用、时间、确认／撤销状态 |
| 生成与草稿 | 输入会话版本、三条机器原稿、修改版本、选用／复制动作、对应 run/case 引用 |

刷新或重新打开时从数据库恢复客户、会话、设置和已保存草稿。消息保留原文，近期相关内容进入生成；长会话摘要关联原消息，未确认事项不能在摘要中变成事实。页面只展示必要上下文，顾问可展开查看和纠正。

本次预算与送礼要求在会话结束后不自动成为长期偏好；顾客真实回复形成新消息，草稿不能冒充顾问已发送历史。历史审计文件继续追加保存，业务数据库负责快速恢复工作，不覆盖旧结果。

### 5. 偏好算法先做到可解释、可纠正

将香型／甜感等商品偏好、语言／篇幅等沟通偏好分别保存。顾客说“我不喜欢甜香”可以形成有来源的偏好候选；“妹妹不喜欢甜香”属于妹妹。顾问常选短稿只能说明顾问的操作倾向，不能直接认定顾客喜欢短回复。未回复、未购买也不直接推断为讨厌产品。

推荐先做确定性筛选：预算硬上限、明确排除项、使用对象和当前要求。再按已确认的香调／甜感匹配排序，初期每个匹配维度等权，保留排序理由与规则版本，不声称已经学得最优权重。未知属性不当作满足条件；无合适商品时说明差距或提出必要问题，不能暗中放松预算。顾问可调整当前条件、停用某条偏好、确认或撤销新提取信息。

模型适合从文字里提出结构化偏好候选，规则负责过滤与解释；只有少量虚构客户时不建立“已训练推荐算法”的说法。后续积累真实选用、修改和顾客反馈，才讨论有数据支持的学习方法。

### 6. Web App 与自动接收聊天

推荐目标结构：响应式网页 → FastAPI 薄入口 → 现有 Python 生成／事实／记录模块；会话存 SQLite，模型继续同一家 API。Streamlit 保留为已有基线，不重复维护两套写作规则。发布时使用持久磁盘、HTTPS 和访问控制；部署平台在设计阶段按实际运行条件选择。PWA 安装入口可后加，安装不会带来微信读取权限。[FastAPI 部署概念](https://fastapi.tiangolo.com/deployment/concepts/)、[PWA 安装条件](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable)

PDF 另要求：若以链接提交，阅卷人应无需账号即可打开。因此，未来正式业务工作台与提交材料／合成资料演示入口分开；提交链接满足免账号查看要求，不暴露真实客户数据或模型配置。本轮没有发布任何链接，也没有向题目中的邮箱发送材料。

第一阶段手动粘贴／导入聊天，先验证消息顺序、续聊和自动草稿逻辑。第二阶段才选择一种企业微信／微信客服真实渠道：客户资料同步、客服消息、顾问聊天存档是需要分别核验的能力，不能因为有客户资料权限就假设可以读任意微信聊天。本次官方渠道页访问失败，账号条件、授权范围和具体接口仍待官方文档与企业后台复核；不引用第三方副本冒充确认。[渠道研究及待核验入口](app-channel-research.md)。

自动草稿设计为：新入站消息落库 → 更新会话版本 → 合并短时间内连续输入 → 生成三条 → 顾问选稿。按消息与设置版本避免重复生成；生成期间出现新消息则把旧结果标为上下文已变化，不冒充最新回复；保留正在编辑的稿件。失败可见，重试关联原记录。初期通过单服务的会话任务即可验证，不引入通用调度平台。

允许按会话关闭自动生成，并查看生成状态和调用次数。输出仍由顾问决定使用，自动发送不随自动生成启用。顾客明确拒绝联系时停止主动召回类草稿，不能靠个性化设置覆盖联系意愿。

## 三、展示实验：下一轮怎样证明改动有效

本轮实际完成的是静态审阅、原始输入／输出对照、50 例历史统计、公开文档核验和备份完整性检查。下面均是**待执行的实验**，不是已测结果。原来的正式 50 例已被看过，下一轮对它们只称回归验证。

### 逐步实验，避免一次改完无法解释效果

| 顺序 | 操作 | 证据与判断 |
| --- | --- | --- |
| 1. 事实修复 | 先只改历史商品身份、规格范围与相关事实装配，固定模型和原有提示；覆盖 BD-103、WAKE-103、REC-103、PRICE-102 和新增同类输入 | 先离线检查输入快照，再少量真实生成；记录产品错字／规格错误／预算误报是否仍出现，不把新输出称为盲测 |
| 2. 中文表达 | 固定修复后的事实，选六场景开发输入做旧写作规则与新规则的同输入对照；记录随机性与所有失败 | 改动规则和示例视为同一写作包，只判断包的效果；如需区分示例贡献，再单独对照。不得因单次变好断言稳定提升 |
| 3. 设置与多轮 | 六个开发诊断例试三档语气；新增六场景各一条至少三轮的消息序列，覆盖改预算、换对象、纠正信息、拒绝联系、已经问过的问题 | 比较事实保持、当前目标回应、避免重复追问；同一故事的所有派生输入保留在同一组 |
| 4. 多语言 | 新增 24 例：六场景 × 英→中、中→英、英→英、混合→中；每例三条 | 语言满足、人物归属、商品／金额／日期保持；由具备相应语言能力的真人评阅自然度。补充组独立导出 |
| 5. 页面与持久化 | 实际打开桌面／手机，修改复制；刷新、重开会话、重启服务、切换客户 | 剪贴板与当前编辑逐字一致；已保存状态恢复；不串客户；图片来自真实浏览器 |
| 6. 版本冻结 | 开发验证后冻结代码、资料、规则和模型参数，再跑正式 50 例回归；如主张未见任务泛化，另建未用于提示和调参的家族隔离测试组 | 保留首轮失败和关联重试，新的 C 仍严格八列；不覆盖 v1 文件，不复用旧结果冒充新版输出 |

24 例语言组比调研中的 18 例建议补了英文→英文，覆盖用户直接用英文连续工作的路径。中英变体仍算同一案例家族，不能用翻译制造独立盲测。此次未承诺每种语言均达到可用标准，真实验证前只记录为计划。

### 评价与通过条件（实施前冻结）

结构、格式、已知价格和身份一致性用程序辅助检查；自然度、任务完成、三稿的选择价值用真实评价者评阅。三类证据分开报告：离线替身测试、真实模型运行、真人评价。AI 审阅可以定位问题，不填真人评分。

沿用现有量表，另记录“每例至少一条愿意直接发送”“每条需要的实质修改”“三稿是否有区别”和实际编辑时长。新旧稿随机排列，隐藏版本标签；评阅人看到相同必要事实，保存具体修改及理由。若只有一位评价者就如实写一位；第二位复核是提高可信度的方法，不冒称 PDF 的硬性人数要求。

建议预先约定：固定验收例不出现关键商品、价格、人物归属或未授权服务承诺错误；三条均是独立完整消息；小规模中文配对中可发送覆盖和编辑负担改善且事实不退步。结果不达标则报告失败，不用改变通过标准或重抽好稿修饰。小样本只报告计数和观察，不能宣称统计显著提升。若发现新严重问题，可新增开发例修复，新增后的再测标为回归。

页面验收包括：未保存修改时点击复制得到当前值；保存失败不能显示已保存；跨客户切换隔离；新客户消息不覆盖编辑；复制不会变为已发送；会话临时偏好不污染长期档案；英文模式不转换币种或地区政策；所有真实生成有可追溯快照。
