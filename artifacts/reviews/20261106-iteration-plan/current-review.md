## 解释原理：按优先级的发现

### P1-1 历史商品 ID 没有解析为规范商品事实，已导致商品名写错

`src/qixu_advisor/data.py:51` 只展开本次 `product_ids`；`data.py:59` 仅在产品推荐、购后关怀、价格异议且未指定商品时加载完整目录。`data.py:61` 随后直接附客户档案，没有解析档案或手填历史中的 `product_id` / `sku_id`。

真实证据：

| 案例 | 实际输入快照 | 机器原稿 | 影响 |
|---|---|---|---|
| BD-103-C1 | `artifacts/runs/formal-v1/cases/BD-103/input.json`：历史试香只有 `product_id=QINGLAN`；`facts.products=[]` | `result.json:8`：“之前您试过的青榄” | 目录规范名是“青岚”，模型从拼音 ID 猜错字；生日场景也会引用历史商品 |
| WAKE-103-C1/C2 | `artifacts/runs/formal-v1/cases/WAKE-103/input.json:89`：本次商品仅砚泊/暮光；历史仍有未展开的 QINGLAN | `result.json:8`、`:12`：“之前您试过青澜”“您之前试青澜” | 只补本次推荐商品仍不足以保证历史回忆准确 |

这里能确认的是**模型实际没收到规范中文名，而且确实写错**；未做对照调用，不能把历史映射缺失称为唯一因果。建议下一轮装配“本次相关商品”和“历史提及商品”的规范名称/标识，并保留各自用途；不要为生日祝福强行注入全商品目录。测试应覆盖两种历史来源、仅 ID 无名称、以及本次选品不含历史商品的情况。

### P1-2 商品子集没有范围说明，模型把局部资料当成完整商品目录

同一装配逻辑只给选择的 SKU，没有 `catalog_scope` 或明确的“未提供不等于不存在”约束。REC-103 本次只提供砚泊 30 mL、青岚 50 mL；原稿却说“青岚目前资料里只有50ml这一规格”（`artifacts/runs/formal-v1/cases/REC-103/result.json:8`）。完整目录实际上也有青岚 100 mL（`data/fictional/products.json:24`）。

这条原稿带有“资料里”限定，不能把它直接当成完整目录的裸断言；但对客读法仍会误导商品规格。建议将规范名称表、可选 SKU 范围与此次筛选范围分开表达；相同香水的规格是否齐全由程序给出，不由模型依据缺项推断。增加“选中子集不能得出全部规格”的定向验证。

### P1-3 话术把内部边界当成服务内容，空泛风格指令无法约束具体写法

`data.py:42`、`:79` 每次提供整份政策。`generation.py:29` 至 `:35` 仅拼接系统规则、场景规则和完整请求事实，没有按沟通目标选择政策，也没有例句装配。`prompts/system.txt:5` 至 `:8` 密集规定不得承诺事项，但没有区分“内部约束”与“这次有必要告诉顾客的信息”。品牌语气只有“具体/温和/克制/自然”的标签（`data/fictional/brand.json:9`）。`data/style_examples/approved.jsonl` 只有空白、没有有效记录，且 `build_messages` 根本没有读取该文件。

不是仅凭主观感觉作此判断，实际原稿包含：

| 场景与证据 | 原稿片段 | 与客户任务的关系 |
|---|---|---|
| BD-101-C2，`artifacts/runs/formal-v1/cases/BD-101/result.json:12` | “我这边不做任何预约承诺” | 只是首次联系的生日祝福，客户没有要求预约 |
| AFTER-001-C3，`artifacts/runs/formal-v1/cases/AFTER-001/result.json:16` | “我不会替您判断留香或适合场合” | 客户刚说收到青岚、闻着舒服并致谢，未询问留香或场合 |
| WAKE-001-C2，`artifacts/runs/formal-v1/cases/WAKE-001/result.json:12` | “我这边没有新的优惠或活动可以告诉您” | 低频问候，主动强调没东西可提供削弱联系理由 |
| WAKE-001-C3，`artifacts/runs/formal-v1/cases/WAKE-001/result.json:16` | “库存和留香表现我这边没有可确认的信息，就不多说了” | 客户没有追问这些未知事实 |

这些表达与 PDF 的自然、私人交流、品牌感目标直接冲突。**不编造事实是约束，不是每次都要念出的免责声明。** 建议用应用可读取、可版本化的写作规则与少量经审阅的虚构微信示例，明确先回应客户这一句话、只提相关事实、未被问到的后台限制不展开。真实未知事实若影响本次选择，仍须如实说明。

用户所说“去 AI 味 skill”应分清两层：给开发助手安装技能可以帮助写规则，但不会自动改变 `build_messages` 发给应用模型的提示。应用需要显式加载规则/示例并记录其版本。公开奢侈品资料可提炼服务语气；品牌宣传文案不能标成真实顾问聊天，也不宜整段套入微信。

### P1-4 50 例并没有真正覆盖多轮追问；也没有语气、篇幅或语言控制合同

逐行统计 `data/cases/dev.jsonl` 与 `holdout.jsonl` 的 `request.conversation_history`：

| 历史消息条数 | 案例数 |
|---|---:|
| 0 | 8 |
| 1 | 41 |
| 2 | 1 |

唯一含顾问消息的是 BD-105（`data/cases/holdout.jsonl:5`）：顾问称档案记昨天生日，客户纠正为今天。**没有任何一例含两次客户发言，因此没有客户→顾问→客户的追问验证**。现有“聊天历史是数组”只代表数据结构能装多条消息，不证明能处理连续对话。

`models.py:22` 至 `:31` 的请求合同没有语气、篇幅、沟通目标、输出语言或会话 ID。`Candidate` 在 `models.py:62`、`:68` 仅限制字符数和至少包含一个汉字；不能验证“三条完整中文消息”的语义质量。`tests/test_generation.py:30` 的六场景共用核心使用相同结构替身；`tests/test_app.py:11` 验证提交/编辑记录路径。它们对软件正确性有价值，不能证明模型自然度或多轮能力。

建议下一轮将“本次目标”和“偏简短/温和/直接”等少量写作设置纳入请求与输入快照。三条之间应是有用的回应策略差异，不是三种夸张人设。优先补多轮纠正、预算改变、收礼人切换、已问过的问题、已选但未发送草稿、客户明确拒绝等案例。用户现已确认“多语音”指多语言输入／输出，不是语音系统。PDF 正式输出仍为中文，多语言补充验证另列。

既有保留集已经被阅读；针对其缺陷调整后再跑，只能称回归验证。若主张新方案对未见任务更好，需要先冻结新的家族隔离案例与评分方法。

### P2-1 有审计文件，但没有可恢复的工作会话，客户档案也没有更新路径

`app.py:134`、`:154`、`:157` 只在 `st.session_state["active_result"]` 放当前结果。只有该值存在才从磁盘读输入快照（`:164`），不存在时直接显示填写提示（`:158`）。没有从持久文件恢复当前客户、对话、编辑草稿的入口。普通页面重绘与全新会话应区分：现有测试已验证普通重绘不重复调用模型，不能据此声称刷新/重新打开仍能续聊。本次未运行浏览器刷新实验；“无法恢复”判断基于缺少持久会话读取路径。

`app.py:149` 的 `parent_run_id` 仅当请求完全相同时用于关联重跑；客户再回复一句改变了请求，就不能充当连续对话的关联键。`records.py:115` 保存选用/编辑反馈但不会把草稿加入真实已发送历史，这是正确边界。需要另有客户/会话/消息 ID 和明确的“已实际发送”状态，不能因为复制就认定客户收到了。

建议把数据拆成长期客户事实、本次会话/临时需求、原始消息、生成结果/草稿四层，再决定 JSON 到 SQLite 的迁移。优先解决可恢复、可追溯和当前任务覆盖旧偏好的逻辑；仅把现有 JSON 搬进数据库不等于解决中断。

### P2-2 复制编辑已经有基础实现，但路径分散，未验证浏览器剪贴板

`app.py:179` 至 `:181` 三条候选是只读文本；`:184` 再选一条，`:188` 在单独文本框编辑；`:200` 至 `:201` 使用底部代码框自带复制按钮。故准确结论是**已有复制与编辑入口，尚未达到在候选中直接改稿/复制**，不是“完全不能复制”。

编辑文本框位于 `st.form`，底部复制区是上次 Python 运行渲染的字符串；当前测试只覆盖提交保存之后的内容，未覆盖用户修改但未保存即点击复制。建议把“未保存编辑稿复制时是否为最新文本”列为真实浏览器验收，不能用 AppTest 的保存断言代替。复制成功、复制被浏览器拒绝、切换候选后草稿是否保留，也需要实际使用路径检查。

主工作区同时出现开发案例（`app.py:70`）、运行 ID（`:163`）、完整事实 JSON 折叠块（`:167`）、人工评价切换（`:271`）。这些内容对开发/提交有用，但不应占据顾问写作的主要注意力。建议主页面集中客户/当前对话、必要商品与本次设置、三张可直接编辑的候选卡；开发案例、评价、配置、资料维护放独立设置/管理入口。美化服务于减少切换，不宜增加“升级套餐”等与工作无关区域。

### P2-3 金额校验会误报预算，同时抓不到商品名拼写问题

`generation.py:46` 将容量后 30 字内的金额视为可能报价。PRICE-102 三条正确写出青岚 100 mL 为 1580 元，同时说客户预算 1400 元，却全部报警（`artifacts/runs/formal-v1/cases/PRICE-102/result.json:20` 至 `:22`）。该警告文字本身已要求人工区分预算与报价，不能报成三次价格错误。

反之 BD-103/WAKE-103 商品名错误均 `warnings=[]`：当前检查只匹配本次已提供的规范商品名，没有校验未解析实体。下一轮至少加入已观察到的“预算紧邻价格”反例，并使事实装配与引用检查协调。保留人工核对，不能用“无警告”代替质量合格。

## 展示实验：本次实际核查与未执行内容

实际做了静态逐行阅读、对 50 例历史长度/角色计数、对照完整商品目录和正式输入快照，以及抽取上述真实候选；阅读旧 AI 审阅辅助定位，再以输入与原稿独立核实。本次没有重跑 50 例，也没有新的测试通过数、模型费用、人工得分或改进比例。既有输出已在本地，仍为 `formal-v1` 及其单例技术重试；不因本次阅读变成新实验。

可保留的工程基础是：UI/CLI 共用生成函数；请求/事实/原始返回/机器稿/人工稿分开；失败留痕；固定八列导出不混入人工编辑；评价预期不进入提示。这些有助于后续迭代及 PDF B/C/E，不必为改成 Web App 重写生成核心。

建议下一轮实际实验按依赖推进，并为每一项保存新的版本、输入与输出：

1. 修正历史商品解析与子集范围；用现成错例做可重复回归，新增未见同类案例检验泛化。
2. 固定一套简洁写作规则与示例，先做少量同输入对照；衡量任务回应、事实、自然度、三条差异和改稿量，而非只数长度。
3. 补多轮案例与目标/语气设置；测试最新需求覆盖旧偏好、客户/收礼人分离、不要重复提问。
4. 实现可恢复的会话与候选内编辑/复制后，再做刷新、切换客户、复制最新稿的真实浏览器路径检查。
5. 正式结果固定后交真实评价者评阅；AI 审阅单列。新的 50 例交付仍严格八列，额外设置和版本存在附属快照/清单，不改正式表头。

## 判断结果：与 PDF 交付的关系

PDF 的核心是六场景、三条完整中文微信候选、自然且有品牌感、A–E 证据。顾问选择仍是产品流程的一部分。网络部署、数据库、插件外壳、语音和自动捕捉并非必交项，但可在确有工作收益时作为迭代能力。

| 用户想法 | 对 PDF 的帮助 | 建议顺序 |
|---|---|---|
| 自然度、真实商品、输出目标/语气 | 直接改善题目核心与 B/C/D/E | 第一优先 |
| 补多轮测试与真实对照 | 直接增强 B/D/E 可信度 | 与内容修复一起做 |
| 临时上下文、客户数据库 | 支撑连贯输入与可复现体验；数据库本身不加分 | 先定数据层次，后落库 |
| 精简主页面、候选内编辑复制、美化 | 支撑顾问选稿和可选演示 | 内容/数据合同固定后 |
| Web App 或插件形态 | 方便使用和演示，不能替代 A–E | 先选择部署/接入目标，复用核心 |
| 偏好分析/推荐 | 可增强个人化，但需证据来源、当前/长期区分和可纠正机制 | 先显式偏好规则，后验证学习 |
| 聊天捕捉与自动生成 | 需明确渠道与取得消息的实际能力；自动草稿仍保留顾问选择 | 后续独立验证，不直接当成自动发送 |

应用当前属于可运行的本地初版，不能据“运行成功”宣布内容达标。C 已有可追溯的 50 例/150 条最终机器候选，但首轮 49/50、补充重试需继续单列。A 历史 AI 对话截图仍须真实补齐；D 人工评价尚未完成；E 已有问题证据和一次结构修复记录，本次自然度/上下文等建议尚无实施后的结果。云部署与界面美化均不会消除这些材料缺口。

以上是迭代依据，不是已完成的新版设计或质量提升报告。旧输入、旧候选和旧提交包应冻结，新方案完成后另建版本，支持用户比较并回滚。
