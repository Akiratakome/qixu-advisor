# 栖序 QIXU：Web App、会话保存与渠道边界调研

记录日期：2026-11-06。范围：只读现有实现、一手技术资料调研、下一版方案；本轮没有部署、接入微信、调用模型或修改业务代码。采用 `research` skill 的一手来源原则。本记录由主 session 委派的研究 agent 编写。

## 1. 拆解任务：先让顾问持续完成工作，再接消息渠道

用户已澄清“多语音”指**多语言输入／输出**，渠道顺序为**独立 Web App → 企业微信／微信客服**。建议下一版围绕一条工作流设计：选客户与会话 → 补本次需求与商品 → 设置语言、语气和长度 → 生成三条 → 原位修改、复制、记录 → 下次继续。

网页形态、数据库和多语言有助于真实使用，但不能代替 PDF 的中文三候选、五十例严格八列、评价及过程证据。正式 C 表仍输出三条完整中文；英文或其他语言输出另存扩展测试，不能通过改变正式表列或语言“完成”原要求。本文的交互与架构判断属于方案，并非已交付功能或平台官方建议。

## 2. 解释原理：现有核心可以复用，浏览器会话不等于业务记忆

| 代码观察 | 对下一版的含义 |
| --- | --- |
| `src/qixu_advisor/generation.py:66` 的 `generate()` 已经独立于 Streamlit；界面与 CLI 共用。 | 在外侧增加 HTTP 入口可以复用事实装配、模型调用、三候选验证、运行证据，不必重写生成器。 |
| `data.py:15`、`:39` 将目录读取和事实装配集中在函数里。 | 先把客户、会话读写接到数据库；商品资料仍可保留版本化小目录。不要为了“数据库化”重做全部模块。 |
| `models.py:22` 没有语言、语气、长度或会话 ID；`:66` 强制候选含中文。 | 多语言不是多加一个下拉框：需要显式版本化输出设置、对应验证与分开导出，保留默认中文约束。 |
| `app.py:154` 使用 `active_result`；`:184` 选稿后进入另一个编辑区域；`:201` 用代码框展示复制内容。 | 改为同一候选卡直接编辑与复制，并从业务会话恢复草稿。 |
| `records.py:64` 保存生成清单，`:115` 追加反馈。 | 运行证据和业务会话承担不同目的：保留原始机器输出，用户修改存新版本，不覆盖正式历史材料。 |

Streamlit 官方明确 Session State 绑定 WebSocket，浏览器刷新会使关联状态重置。因此，现有记录文件虽然已经落盘，仍需客户／会话索引和恢复入口来解决“感觉中断”。这是代码观察与官方行为共同支持的结论。[Streamlit Session State](https://docs.streamlit.io/develop/api-reference/caching-and-state/st.session_state#caveats-and-limitations)

### 建议的数据分层

以下是方案，不是当前实现：

| 对象 | 保存内容 | 必要边界 |
| --- | --- | --- |
| 客户 `customer` | 称呼、顾问关系、明确的长期偏好、已确认联系意愿 | 购买者和收礼人用独立主体；本次送礼喜好不自动写成购买者长期喜好。 |
| 会话 `conversation` | 客户 ID、本次需求、场景、语言／语气／长度设置、未解决问题、最近打开时间 | 同一客户可以有多次会话；临时需求关闭后不永久影响下次推荐。 |
| 消息 `message` | 作者、正文、时间、来源、外部消息 ID（未来渠道使用） | 模型草稿与真正已发送消息分开。点击复制只记“复制”，不能记成顾问已发送。 |
| 生成与编辑 `generation` / `draft_revision` | 生成使用的会话版本、三条原稿、编辑稿、选用动作、对应 run/case ID | 新消息到来不覆盖顾问正在编辑的文字；结果标注所属上下文版本。 |
| 偏好 `preference` | 主体、偏好类别、值、原文来源、时间、明确／推测、状态 | 推测项可撤销或确认；顾问喜欢选短稿不等于顾客喜欢短回复。 |

近期原文和本次需求应优先进入生成快照；长会话可以增加摘要，但摘要必须关联原消息、保留未确认事项，并允许顾问修正。首版小规模文本可先限量选取相关历史，不必引入向量库。语言偏好也需区分“此次输出英文”和“长期偏好英文”。

当前只有小商品目录和少量虚构客户，建议先做可解释排序：先满足明确预算、收礼对象和排除偏好，再按已确认香调／场景匹配排序，显示“因哪条事实推荐”。同一条件下没有匹配商品时说明缺口。顾客没有回复或没有购买不能作为“反感香型”的可靠证据。没有真实反馈数据时，不声称已训练偏好模型。

## 3. 展示实验：已核验的 Web 能力与未核验的渠道权限

本节“实验”是文档核验和代码检查；没有执行新的浏览器复制实验、部署实验或微信真实收发。待实施的验收在第 5 节。

### 3.1 独立 Web App 的实现取舍

| 选项 | 官方已核验事实 | 本项目判断 |
| --- | --- | --- |
| 保留 Streamlit 并托管 | Community Cloud 从仓库根目录运行应用，支持依赖配置与应用设置中的 secrets。[部署文件组织](https://docs.streamlit.io/deploy/streamlit-community-cloud/deploy-your-app/file-organization)、[密钥配置](https://docs.streamlit.io/deploy/streamlit-community-cloud/deploy-your-app/secrets-management) | 本地并非 Streamlit 的必然限制。若目标只是可访问演示，托管是较小改动；但不能仅上传代码就宣称有持久 CRM。本次未核实某一托管套餐的磁盘持久承诺。 |
| 独立网页 + FastAPI 薄入口 + 原 Python 核心 | FastAPI 的部署文档覆盖 HTTPS、进程启动／重启；HTTPS 通常由代理或托管平台提供。[官方部署概念](https://fastapi.tiangolo.com/deployment/concepts/) | 推荐下一版目标结构：满足三稿原位编辑、响应式布局、客户会话恢复，并为未来渠道复用一个服务。前端可用轻量组件实现；无需一开始建设微服务、队列集群或重选模型供应商。 |
| PWA 安装外观 | 支持的浏览器可把网页安装到设备，以独立窗口启动；安装支持因平台而异。manifest 和 HTTPS／本地开发地址是关键条件；service worker 并非安装的一概前提。[MDN PWA 安装](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable) | 在 Web 工作流稳定后增加图标和安装入口。PWA 不等于离线模型，也不会赋予读取微信聊天的权限；不把“可安装”误写成已经完成原生 App。 |

建议先用一个部署实例、一个 Python 服务和该实例的持久磁盘；数据库文件及新增证据写入配置的数据目录，而不是把运行目录当临时容器文件。密钥仅由服务端读取。对外演示仅用合成资料；真实业务使用时再依据实际用户范围配置身份和数据访问，演示链接的可访问要求不等于客户库应公开。

SQLite 官方认为其可服务低至中等流量网站，但同一数据库同一时刻只允许一个写入者；多机器直接共享数据库文件、写入压力较大或需要多台应用服务器时更适合客户端／服务端数据库。[SQLite 适用范围](https://www.sqlite.org/whentouse.html)

**据此的选型判断：**少量顾问通过同一个应用服务操作，短事务写入的 SQLite 足以作为下一版演示／小规模试用方案；“多人”本身不是必须改 PostgreSQL 的充分条件。实际需要多个应用实例并行写、持续写冲突或集中数据库运维时，再转 PostgreSQL。模型网络调用应位于数据库写事务之外，避免等待模型期间占用写锁。不要把 SQLite 文件放在多台服务器共享的网络目录来假装完成扩容。

### 3.2 一键复制与原位修改

`navigator.clipboard.writeText()` 写入指定文本，成功 Promise 完成后才表明系统剪贴板已更新，且要求安全上下文。[MDN writeText](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard/writeText) Clipboard 规范允许浏览器控制写入权限，浏览器行为并不完全一致：Chromium 写入依赖权限或临时用户激活；Safari、Firefox 写入要求临时用户激活。[W3C Clipboard 权限](https://w3c.github.io/clipboard-apis/#clipboard-write-permission)、[MDN 浏览器差异](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API#security_considerations)

**设计结论：**每张候选卡使用可编辑文本框，按钮直接读取该框当前值，在点击处理函数内调用写入；不要先等待后端保存再复制，以免丢失用户激活。复制完成再提示“已复制”，失败保留文字并提供选中文字手动复制。保存编辑和复制是分别可追踪的操作。三个候选 ID 稳定，重新生成产生新组；不静默替换正在编辑的候选。无需请求读取整个系统剪贴板的权限。

主页面只呈现客户／会话、当前需求、相关商品和三条候选；语言、语气、长度为紧邻生成操作的简短设置。客户资料维护、模型配置状态、导入／导出、测试集和评价移到设置或管理入口。移动端设置使用可关闭抽屉，不用默认展开侧栏挤压正文。复制、恢复和修改的可用性比装饰性品牌大标题优先。

## 4. 判断结果：先交付业务连续性，渠道自动化后置验证

建议分三步迭代：

1. **工作质量与会话模型。**先修商品事实和文案风格，确定语言／语气／长度语义；建立客户与会话存储、原稿和修改版本。保留 PDF 默认中文输出和原有证据链。
2. **独立 Web 工作台。**复用 Python 核心建立薄服务层，三候选直接编辑复制，设置从主页面收起，刷新能恢复会话；在单实例持久盘上验证部署。PWA 安装为后续小增量。
3. **渠道试点。**官方权限核实后选一种真实路线，先完成“入站消息 → 会话版本更新 → 自动生成三条草稿 → 顾问检查”。自动发送应作为独立能力设计，不能由“自动生成”隐含启用。

未来入站接入至少保留 `channel`、外部会话／消息 ID、作者、收到时间和内容。重复通知不重复入库或重复收费；同一客户连续消息可合并为一次待生成上下文；人工正在编辑时提示有新消息而不覆盖草稿。生成快照引用明确消息集合，区分“通道真实读取”“用户粘贴”“合成测试”。这组行为是小规模试点必需的业务正确性，不要求先建通用调度平台。
